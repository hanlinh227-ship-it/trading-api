# Harmonized Skills Expansion — Design

Date: 2026-09-13
Status: Design approved in chat; written spec awaiting review; implementation not started
Canonical repository: `hanlinh227-ship-it/trading-api`
Canonical branch: `main`

## 1. Purpose

Expand the current GitHub Brain skill surface without creating a parallel reasoning authority, duplicate router ownership, mandatory local dependencies, or uncontrolled provider/plugin behavior.

The expansion adds only capabilities that are materially distinct from current canonical skills and strengthens existing canonical skills when an upstream skill is semantically equivalent. Every imported pattern remains evidence/reference input until it passes the existing harmonization, provenance/license, conflict, security, eval, canary, validator, and immutable-release gates.

The Stable Runtime Plane must remain fully usable while the Evergreen Update Plane evaluates the new capability set.

## 2. Current authority and invariants

This design inherits the current checkpoint-resolved authority chain and does not replace it.

Required invariants:

1. Every handled request still routes through `task_router`.
2. Exactly one primary reasoning skill is selected for every routed request.
3. Supporting skills remain bounded by the active runtime profile and never become a voting authority.
4. Provider/plugin/upstream repositories remain capability or evidence inputs, not reasoning authority.
5. Current runtime evidence and current project authority outrank imported guidance.
6. Equivalent upstream skills strengthen a canonical skill or become aliases/adapters; they do not create duplicate primary ownership.
7. One trigger term has one canonical owner after compilation.
8. Stable security, permission ceilings, project isolation, and live-data freshness rules cannot be weakened.
9. Financial, credential-sensitive, destructive, and execution-expanding capabilities never auto-promote.
10. Normal research remains zero-local: no required user installation of Node, npm, Python, MCP servers, exchange bundles, or provider CLIs.
11. Retrieval index and release manifests are generated by the canonical tools, never edited by hand.
12. The existing Skill Gateway Cloudflare runtime and Railway live-price research runtime remain separate unless a dedicated runtime migration is independently designed and verified.

## 3. Design strategy

Use a `create / strengthen / alias / reject` decision for every candidate capability.

```text
candidate source
    -> provenance + license
    -> quarantine
    -> normalize capability contract
    -> overlap scan
    -> conflict + security scan
    -> decision
         create      only for materially distinct capability
         strengthen  when equivalent to existing canonical skill
         alias       when terminology differs but purpose is identical
         reject      when unsafe, redundant, unlicensed, incompatible, or dependency-heavy
    -> domain evals
    -> routing regression
    -> canary
    -> validator suite
    -> immutable release
    -> production verification where runtime-affecting
```

No external repository is copied wholesale. Only documented patterns and, where license permits and code reuse is justified, small isolated helper logic may be absorbed.

## 4. New canonical skills

### 4.1 `skill_engineering`

Domain: `engineering`

Purpose: design, revise, normalize, and validate AI skill definitions for this repository.

Distinct capability: the current catalog can route and execute skills, but it does not have a canonical reasoning skill whose user-facing purpose is to engineer new skills themselves.

Primary triggers include:

- create a skill
- design a skill
- update a skill
- skill manifest
- skill contract
- skill registry design
- normalize a skill

Primary responsibilities:

1. Define concrete usage examples and intended triggers.
2. Scan the canonical catalog for semantic overlap before creation.
3. Choose `create`, `strengthen`, `alias`, or `reject`.
4. Define concise metadata and lazy-loaded procedural content.
5. Define inputs, outputs, tools, sources, permissions, risk ceiling, exclusions, and eval requirements.
6. Preserve progressive disclosure: metadata first, body when triggered, detailed references/scripts only when required.
7. Produce or update the execution-capsule contract required by the existing gateway compiler.
8. Keep skill-specific documentation lean and avoid duplicate reference content.
9. Route promotion through existing Evergreen gates rather than granting authority directly.

Explicit exclusions:

- general software architecture -> `software_architecture`
- ordinary coding -> `coding`
- debugging a runtime defect -> `debugging`
- evaluating whether a skill improves quality -> `eval_engineering`

Upstream references:

- `openai/skills` skill-creator patterns: concise skill definitions, progressive disclosure, optional scripts/references/assets, validation.
- `agentskills/agentskills` specification: SKILL-style packaging and portable capability metadata.

Neither upstream becomes runtime authority or a required dependency.

### 4.2 `eval_engineering`

Domain: `engineering`

Purpose: design and execute evaluation methodology for skills, routing, prompts, capability adapters, and Brain behavior changes.

Distinct capability: current verification/eval infrastructure exists, but there is no user-facing canonical skill dedicated to constructing and interpreting eval suites for new or changed AI capabilities.

Primary triggers include:

- evaluate this skill
- benchmark this skill
- regression test this skill
- compare skill versions
- build an eval suite
- canary this capability

Primary responsibilities:

1. Establish a verified baseline before candidate comparison.
2. Build representative positive, negative, boundary, and adversarial cases.
3. Measure routing correctness, output-contract correctness, conflict handling, security behavior, context cost, and domain quality.
4. Protect current invariants with zero-tolerance regressions on protected dimensions.
5. Separate deterministic validation from model-graded quality checks.
6. Record evidence and outcomes without persisting hidden chain-of-thought.
7. Recommend `promote`, `revise`, or `reject`; it does not self-promote a candidate.

Explicit exclusions:

- final implementation verification of ordinary code -> existing `verification`
- test-driven implementation workflow -> `tdd`
- generic comparison request -> `comparison`

Reference patterns may be absorbed from OpenAI skill validation and the existing Brain eval/promotion framework, but this skill remains native to the repository.

### 4.3 `quant_validation`

Domain: `trading`

Purpose: audit quantitative trading research and backtest claims for methodological validity.

Distinct capability: `quant_backtesting` constructs or runs quantitative tests; `quant_validation` independently evaluates whether the resulting evidence is statistically and operationally credible.

Primary triggers include:

- validate this backtest
- check overfitting
- check data leakage
- lookahead bias
- survivorship bias
- walk-forward validation
- out-of-sample validation
- transaction-cost realism
- multiple-testing bias

Primary responsibilities:

1. Detect train/test contamination and feature/label leakage.
2. Detect lookahead and timestamp alignment errors.
3. Check survivorship and universe-selection bias.
4. Check transaction costs, spread, slippage, funding, commissions, and impact assumptions when material.
5. Check sample size, trade dependence, regime concentration, and instability.
6. Require appropriate holdout or walk-forward evidence for optimization claims.
7. Distinguish parameter search performance from genuine out-of-sample evidence.
8. Flag repeated search / multiple-testing effects and unrealistic target forcing.
9. Report uncertainty and methodological failure instead of optimizing toward a predeclared win rate.
10. Remain analysis-only/read-only; it never grants execution authority.

Upstream reference:

- `ml4t/skills` concepts for data leakage, survivorship bias, transaction costs, causal/statistical validation, and systematic backtest failure modes.

License/provenance must be recorded in Evergreen metadata. No upstream runtime is required.

### 4.4 `asset_validation_3d`

Domain: `design_3d`

Purpose: independently validate 3D assets and Blender-oriented deliverables after creation or modification.

Distinct capability: existing `modeling`, `topology`, `uv`, `materials`, `lighting`, `rigging`, `animation`, `rendering`, and `blender` skills create or modify artifacts. None has validation as its sole primary purpose.

Primary triggers include:

- validate this 3D asset
- check Blender model
- inspect topology
- validate export
- check normals/scale/transforms
- inspect asset from multiple views

Primary responsibilities:

1. Check geometry integrity and obvious mesh defects.
2. Check scale, transforms, origins, normals, naming, and scene cleanliness when relevant.
3. Check topology for the target use case rather than applying one universal topology rule.
4. Check UV/material consistency when required by the asset contract.
5. Check rig/animation compatibility when present.
6. Inspect the asset from multiple relevant views before acceptance.
7. Validate export settings against the target format/use case.
8. Prefer a fresh re-import or equivalent independent verification for final export validation when tools permit.
9. Report pass/fail/conditional findings rather than silently modifying the asset unless the routed task explicitly requests correction.

Upstream reference:

- `ifBars/blender-agent-studio` workflow patterns for iterative visual verification, multi-view inspection, and asset/export quality control.

The upstream project remains reference-only; its npm/package/runtime stack is not a required dependency.

## 5. Existing canonical skills to strengthen

### 5.1 `security`

Strengthen with repository-grounded threat-modeling patterns:

- derive components and entry points from repository evidence;
- distinguish runtime surfaces from CI/dev/test tooling;
- enumerate trust boundaries and assets;
- model realistic attacker capabilities and explicit non-capabilities;
- describe threats as concrete abuse paths;
- rank likelihood and impact with stated assumptions;
- tie mitigations to concrete components/locations;
- avoid generic checklist-only threat reports.

Do not create a parallel `security-threat-model` canonical skill unless future evidence shows a materially distinct primary purpose that cannot be represented by `security` plus bounded supporting context.

### 5.2 `debugging`

Strengthen with GitHub Actions/CI diagnosis patterns:

- identify the failing check;
- inspect the correct run/job logs;
- separate GitHub Actions evidence from external CI providers;
- summarize the failure before proposing changes;
- implement only through the existing approval/development discipline;
- re-check status after the fix.

Do not create a duplicate `gh-fix-ci` primary skill. GitHub-specific terminology may be represented by trigger aliases that compile into `debugging`.

### 5.3 `ux_ui` and `product_design`

Strengthen with design-system and design-to-code verification patterns where current connected tooling permits:

- derive reusable component/token rules from the current design system;
- maintain component and interaction consistency;
- preserve accessibility constraints;
- verify implementation against the source design rather than relying on visual memory;
- prefer exact source artifacts when available.

Do not create multiple Figma-branded reasoning authorities. Figma remains a tool/capability provider beneath canonical design skills.

### 5.4 `quant_backtesting`

Clarify its boundary with `quant_validation`:

- `quant_backtesting`: construct, run, instrument, and reproduce backtests/experiments;
- `quant_validation`: independently audit whether conclusions are credible.

A single request may use one as primary and the other as a bounded supporting skill only when the active profile permits it. There is never a vote between them.

## 6. Router changes

Add the four new canonical skill IDs to their existing domains:

- engineering: `skill_engineering`, `eval_engineering`
- trading: `quant_validation`
- design_3d: `asset_validation_3d`

Routing constraints:

1. Preserve exactly one primary skill.
2. Resolve overlapping trigger phrases before promotion.
3. `skill_engineering` must not steal generic `architecture`, `code`, or `debug` traffic.
4. `eval_engineering` must not steal ordinary final verification or TDD traffic.
5. `quant_validation` owns methodological-audit intent; `quant_backtesting` owns building/running the experiment.
6. `asset_validation_3d` owns validation/audit intent; creation/editing remains with existing 3D skills.
7. Upstream source names such as OpenAI Skills, Agent Skills, ML4T, Blender Agent Studio, Figma, or GitHub Actions do not themselves determine reasoning authority.

Representative expected routes:

| Request | Expected primary |
|---|---|
| Create a new skill for Blender export checks | `skill_engineering` |
| Benchmark two versions of this skill | `eval_engineering` |
| Backtest this strategy across 10 coins | `quant_backtesting` |
| Audit this 100-trade backtest for leakage and overfit | `quant_validation` |
| Model this prop in Blender | `blender` |
| Check whether this Blender asset is export-safe | `asset_validation_3d` |
| GitHub Actions is failing | `debugging` |
| Threat-model this repository | `security` |

## 7. Manifest and registry changes

Update only canonical sources required by the new skill surface.

Expected authored files:

- `AI_SKILL_LIBRARY/skills/catalog.yaml`
- `AI_SKILL_LIBRARY/v4/stable/router.yaml`
- `AI_SKILL_LIBRARY/v4/skills/engineering/manifest.yaml`
- `AI_SKILL_LIBRARY/v4/skills/trading/manifest.yaml`
- `AI_SKILL_LIBRARY/v4/skills/design_3d/manifest.yaml`
- checkpoint-resolved capability/harmonization or Evergreen source metadata only where the existing schema requires explicit upstream mapping
- routing/eval tests

Generated artifacts must not be manually edited:

- retrieval index
- compiled Skill Gateway snapshot
- immutable release manifests/hashes/history

Those are rebuilt through the checkpoint-declared canonical tools.

## 8. Capability fusion and external-source policy

The following sources are approved for evaluation as references, subject to final provenance/license capture:

1. `openai/skills`
   - absorb: concise skill design, progressive disclosure, deterministic validation patterns, repository-grounded security/CI workflows where relevant;
   - do not absorb: product-specific assumptions that require unavailable local tooling.

2. `agentskills/agentskills`
   - absorb: portable SKILL packaging concepts and metadata compatibility;
   - do not make the external specification a routing authority.

3. `ml4t/skills`
   - absorb: quantitative-research failure modes and validation concepts;
   - do not import a large parallel catalog or let popularity become authority.

4. `ifBars/blender-agent-studio`
   - absorb: iterative multi-view asset inspection and export-validation patterns;
   - do not require its package/runtime or copy the full agent framework.

Candidate repositories with unclear licensing, credential requirements, mandatory local runtimes, hidden permission expansion, autonomous financial execution, or parallel-agent voting authority remain quarantined or rejected.

## 9. Security and permission ceilings

`skill_engineering`: may author repository skill definitions only under the existing write/approval discipline. It cannot expand its own permissions.

`eval_engineering`: read/analysis by default; any test artifact writes are reversible repository changes under normal engineering controls. It cannot promote a candidate by itself.

`quant_validation`: read-only analysis. It cannot place/cancel/amend orders, change leverage, touch wallets, move funds, or mutate account state.

`asset_validation_3d`: validation-only by default. Artifact modification requires the task to route to the appropriate creation/editing workflow or explicit approved corrective work.

No new skill may weaken the current financial or credential-sensitive fail-closed boundaries.

## 10. Evaluation design

### 10.1 Routing evals

Add positive and negative routing cases for every new skill and strengthened overlap.

Minimum categories:

- exact trigger
- paraphrase
- neighboring canonical skill
- ambiguous request
- negative/excluded request
- source/provider name without actual task intent

Protected condition: no existing representative route may silently change unless the design explicitly requires it.

### 10.2 Skill-contract evals

For each new skill verify:

- one unique canonical ID;
- domain membership;
- valid execution capsule;
- declared tools/sources/permissions;
- risk ceiling;
- output contract;
- no forbidden alias-as-primary state;
- no duplicated trigger owner after compilation.

### 10.3 Domain evals

`skill_engineering`:

- detects duplicate skill proposals;
- selects strengthen/alias instead of duplication when appropriate;
- produces concise/lazy-loadable definitions;
- refuses hidden permission expansion.

`eval_engineering`:

- establishes baseline;
- catches protected regressions;
- separates deterministic and qualitative evaluation;
- cannot self-promote.

`quant_validation`:

- detects obvious leakage/lookahead fixtures;
- flags unrealistic no-cost backtests where costs are material;
- distinguishes in-sample optimization from out-of-sample evidence;
- rejects forced performance conclusions unsupported by evidence.

`asset_validation_3d`:

- identifies representative geometry/normal/scale/export defects from fixtures or structured test metadata;
- does not steal asset-creation routing;
- requires multi-view/export verification when the contract calls for it.

### 10.4 Global regression

Run the canonical CI validation entrypoint and all required Brain/router/authority/registry/Skill Gateway tests.

The protected regression tolerance remains zero for correctness, authority, security, verification, and project isolation.

## 11. Implementation sequence

Implementation must follow this order:

1. Refresh current `main` and checkpoint before edits.
2. Create routing/eval tests that fail for the missing new skill behavior where practical.
3. Add minimal catalog rows and domain manifest membership.
4. Add router ownership for the four new canonical skills.
5. Strengthen the existing `security`, `debugging`, design, and quantitative contracts without introducing duplicate authorities.
6. Add or update capability-fusion / Evergreen provenance metadata for the approved upstream references if required by current schemas.
7. Run targeted tests until GREEN.
8. Run registry, router, authority, runtime, V4, Skill Gateway, and global validators through the canonical CI entrypoint.
9. Rebuild generated retrieval/snapshot artifacts through canonical tools.
10. Run routing regression matrix and context-budget checks.
11. Build the next immutable release with the canonical release tool; do not hard-code a release number in source-of-truth instructions.
12. Promote only if every required gate passes.
13. If runtime files changed, complete the existing production deployment verification contract; if this remains metadata-only, do not claim a runtime rollout that did not occur.
14. Record verification evidence and keep the previous verified release as rollback target.

## 12. Failure and rollback behavior

If any required gate fails:

- do not partially promote;
- do not mutate the active Stable snapshot;
- keep the last verified Stable release serving requests;
- keep candidate skills in quarantine/revision state;
- report the failing gate and evidence;
- rollback does not require a complete root-cause analysis before restoring the previous verified release.

If an external reference disappears or becomes incompatible after promotion, the native canonical skill must continue functioning from its repository-owned contract. External runtime dependency failure must not disable Stable reasoning.

## 13. Non-goals

This expansion does not:

- build a second router or second Brain;
- replace project authorities;
- migrate live-price runtime from Railway;
- enable automated trading execution;
- install local software on the user device;
- import entire third-party skill catalogs;
- use majority voting between agents/skills as truth;
- let plugins define reasoning authority;
- grant permissions because a provider or repository exposes a capability;
- guarantee better quality merely from a larger skill count.

## 14. Acceptance criteria

The expansion is complete only when all of the following are true:

1. Four new canonical skills exist: `skill_engineering`, `eval_engineering`, `quant_validation`, `asset_validation_3d`.
2. Each has one unambiguous primary-purpose boundary and a validated execution capsule.
3. `security`, `debugging`, `ux_ui`/`product_design`, and `quant_backtesting` incorporate the approved strengthening patterns without duplicate primary authorities.
4. Router tests prove the representative route matrix and overlap negatives.
5. The compiled catalog has no duplicate trigger ownership or routable alias rows.
6. Provenance and license status are recorded for every absorbed upstream source.
7. Financial/read-only boundaries remain unchanged or stricter.
8. Zero-local operation remains preserved.
9. Canonical validators and global regression suites pass.
10. Generated retrieval/snapshot/release artifacts are produced by canonical tooling.
11. The candidate is promoted atomically as an immutable release only after all gates pass.
12. No claim of production deployment or LIVE state is made without corresponding runtime verification.

## 15. Design decision

Proceed with the Harmonized Skills Expansion as a bounded extension of the existing V4 LTS dual-plane architecture. The design deliberately favors a small number of orthogonal canonical skills plus strengthened existing skills over bulk-importing third-party catalogs.

This preserves the repository's current authority chain, skill budget, zero-local runtime model, security posture, and rollback discipline while adding meaningful capability in skill engineering, evaluation engineering, quantitative validation, and 3D asset validation.
