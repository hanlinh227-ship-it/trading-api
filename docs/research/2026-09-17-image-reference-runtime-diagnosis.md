# Image Reference Runtime Diagnosis — 2026-09-17

## Scope

Why the reference-safe image runtime reported `provider_request_failed` for
`REFERENCE_GENERATION`, `INPAINT` and `VISUAL_CRITIC`, and what is actually
blocking each one. Every line below is production evidence from the Image Render
production smoke on exact main `77a898516367fb753732b10ef31ab427ee79fe64`,
GitHub Actions run `35176342141`, not inference from documentation.

Until this run the smoke printed only `detail=provider_request_failed`. One
failure string stood for four different causes, so the subsystem had been
reporting "no reference-safe free runtime" without anyone being able to say why.
The smoke now prints each probe's sanitized diagnostic and every model the task
chain rejected.

Four distinct causes, one of which was ours.

## 1. The probe was sending broken images (ours, fixed)

`3005 ... broken data stream when reading image` is a decoder error, not a
missing runtime. The probe carried its image and mask as base64 literals. Both
were truncated:

- probe image: 651 bytes on disk; its `IDAT` declares 798 bytes and the chunk
  walk runs to 843. No `IEND`.
- probe mask: 758 bytes on disk against a required 842. No `IEND`.

The inpainting model was reachable the whole time and was being handed a corrupt
PNG. `INPAINT`, `IMAGE_EDIT_LOCAL`, `BACKGROUND_REPLACE`, `OBJECT_REPLACE` and
`TARGETED_REPAIR` were all reported dead on that evidence.

Probe images are now generated by a checked-in PNG writer and asserted
structurally — signature, chunk order, per-chunk CRC, exact end-of-file, and a
pixel round trip through inflate — so a probe asset cannot silently rot again.

The same corrupt bytes were being handed to `llava`, which is the likely cause of
its `3010: Unsupported image data`. The critic also received a `data:` URL string
where Workers AI vision models take an array of 8-bit values; both are fixed.
Whether `llava` then works is an empirical question for the next production run;
it is not asserted here.

## 2. SDXL base cannot do image-to-image here (ours, fixed)

The Cloudflare model page for `@cf/stabilityai/stable-diffusion-xl-base-1.0`
lists `image[]` and `mask[]` among its parameters. The runtime disagrees:
`3030: input tensor 'image' is not present in the model`. It was added to the
image-conditioned fallback chains on the strength of that parameter list, which
was wrong.

SDXL base is now a text-to-image fallback only. **The runtime is the authority on
what a model accepts; a documented parameter list is not.**

## 3. img2img is blocked at the account level (not ours)

`5018: This account is not allowed to access
@cf/runwayml/stable-diffusion-v1-5-img2img` is an authorization decision on
Cloudflare's side. No code change reaches it.

The mitigation that does not need it: an inpainting model given a fully-editable
mask *is* image-to-image. `@cf/runwayml/stable-diffusion-v1-5-inpainting` is
accessible on this account, so it now backs `REFERENCE_GENERATION`,
`IMAGE_EDIT_GLOBAL` and `STYLE_TRANSFER`, with the mask synthesized when the
caller has none to give. Whether it succeeds is for the next production probe to
say.

## 4. The visual critic needs a licence acceptance (not ours, needs the account owner)

`5016: Prior to using this model, you must submit the prompt 'agree'. By
submitting 'agree', you hereby agree to the llama-3.2-11b-vision-instruct
Community License`.

This is a one-time acceptance of Meta's licence by the account owner. Accepting a
licence on someone's behalf is not a code change and was not done. Until it is
accepted — or `llava` proves out as the fallback — `visualCriticRuntime` stays
`UNAVAILABLE` and STRICT renders finish `complete_unverified`, which is the
honest result and the behaviour the quality policy already specifies.

## Standing blockers

1. **Cloudflare account authorization for `@cf/runwayml/stable-diffusion-v1-5-img2img`** (`5018`).
   Not reachable from code. The inpainting route is the mitigation.
2. **Meta Llama 3.2 Vision licence acceptance** (`5016`). Requires the account
   owner to submit `agree` for that model. Deliberately not automated.

Neither is a reason to reach for a paid provider: `paid_fallback` stays `false`,
`auto_purchase` stays `false`, and work with no safe free runtime waits as
`WAITING_FOR_SAFE_FREE_RUNTIME` rather than being re-routed or silently dropped.

## What this run did prove

Scene 1 — two locked character references plus a locked background,
`CONFIDENTIAL`, submitted through the canonical V3 job path — reached the
reference-safe provider and never touched the volunteer provider
(`IMAGE_SCENE1_REFERENCE_SAFE=PASS`, `providers=none` on AI Horde). The routing
continuity fix holds in production. The render itself did not happen: the job
ended `waiting_for_safe_free_runtime`, which is the correct report for a
reference-safe runtime that rejected every model it had.
